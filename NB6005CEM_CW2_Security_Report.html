Abstract

This report documents the security implementation of SecureBank, a prototype secure banking application developed as Coursework 2 (CW2) for the NB6005CEM Network Security module. Building upon the system architecture designed in CW1 — which specified a banking environment comprising network infrastructure, managed switches, application servers, and a database layer — CW2 required the realisation of that design as a functional prototype with security applied at three distinct levels: algorithm-level, protocol-level, and system-level.

The prototype is implemented using a React/Vite frontend and a Python FastAPI backend, with a cloud-hosted TiDB (MySQL-compatible) database accessible over TLS. Algorithm-level security includes Argon2id password hashing, AES-256-GCM field-level encryption for sensitive database columns, ECDSA (P-256) digital signatures for transaction non-repudiation, and HMAC-SHA256 integrity tagging. Protocol-level security encompasses HTTPS/TLS 1.3 for all API traffic, RS256 JSON Web Tokens (JWT) for stateless authentication, TOTP-based Multi-Factor Authentication per RFC 6238, and SMTPS (Implicit TLS, port 465) for transactional email notifications. System-level security includes a software-based Intrusion Detection System (IDS) middleware, rate limiting, account lockout, Role-Based Access Control (RBAC), and least-privilege database user segregation. The report critically evaluates each control, justifies algorithmic choices against alternatives, and maps all mechanisms back to the vulnerability points identified in the CW1 design.

1. Introduction

Coursework 1 (CW1) for NB6005CEM required the design of a secure banking system architecture, addressing network topology, trust boundaries, data flows, and potential attack surfaces. The resulting design specified a multi-tier environment comprising: an external user-facing network layer, a managed Layer-2/3 switch fabric enforcing VLAN segmentation, a hardened application server tier, and a consolidated database unit. The CW1 design identified key vulnerability points — unauthenticated data transmission, weak credential storage, absent audit trails, and insufficient access controls — and proposed mitigations through the placement of firewalls, encryption points, and access control boundaries on the system diagram.

CW2 requires the construction of a working prototype that instantiates those security controls in real, executable code. SecureBank is that prototype. It is a browser-based banking application with a React/Vite frontend (served at localhost:5173), a FastAPI backend (served over HTTPS at https://localhost:8443), and a cloud-hosted TiDB database (AWS us-west-2, accessed over TLS on port 4000). The system supports customer registration, two-factor login, fund transfers, transaction history, and an administrator dashboard with audit log visibility and fraud review capabilities.

Security is applied at three levels as required by the CW2 specification. First, at the algorithm level, specific cryptographic primitives are selected and implemented in the backend security modules. Second, at the protocol level, industry-standard secure communication protocols govern all data exchange between system components. Third, at the system level, procedural and architectural controls harden the runtime environment against attacks not addressed by cryptography alone.

2. Security Analysis

2a. Algorithm-Level Security (40%)

Algorithm-level security refers to the selection and correct application of cryptographic algorithms — the mathematical primitives that underpin confidentiality, integrity, and authenticity. Four distinct mechanisms are implemented in SecureBank, each targeting a specific attack surface.

2a.1 Password Hashing — Argon2id Control Point G

Technical Mechanism. Argon2id is a memory-hard, time-hard key derivation function standardised as the winner of the Password Hashing Competition (PHC) in 2015 (Biryukov et al., 2016). It operates by filling a configurable amount of RAM with pseudo-random data during the hashing computation. The id variant hybridises the data-independent memory access of Argon2i (which resists side-channel attacks) with the data-dependent access of Argon2d (which resists GPU-optimised attacks), making Argon2id the recommended choice for general password hashing (Josefsson & Liusvaara, 2019). The output is a self-describing hash string containing the algorithm parameters, a unique 16-byte random salt, and the derived hash.

Configuration Applied. The implementation in security/password.py uses the argon2-cffi library with OWASP-recommended parameters (OWASP, 2021): 

ph = PasswordHasher(
    time_cost=2,       # 2 iterations
    memory_cost=19456, # 19 MB RAM per hash — resists GPU parallelism
    parallelism=1,
    hash_len=32,       # 256-bit output
    salt_len=16        # 128-bit random salt
)

2a.2 Field-Level Encryption — AES-256-GCM Control Point I

Technical Mechanism. AES (Advanced Encryption Standard) is a symmetric block cipher standardised by NIST in FIPS 197 (NIST, 2001). The GCM (Galois/Counter Mode) operating mode transforms AES into an Authenticated Encryption with Associated Data (AEAD) scheme. GCM generates a keystream from a unique nonce and the block counter using AES in counter mode; it simultaneously computes a GHASH-based authentication tag (McGrew & Viega, 2004). This means GCM provides both confidentiality and integrity without a separate HMAC operation.

Application in the System. The security/field_crypto.py module applies AES-256-GCM to two sensitive database columns: the TOTP MFA shared secret (users.mfa_secret_encrypted) and National ID number (accounts.national_id_encrypted). A fresh 96-bit nonce is generated per encryption call via os.urandom(12): 

aesgcm = AESGCM(KEY)              # 256-bit key from FIELD_ENCRYPTION_KEY env var
nonce  = os.urandom(12)           # 96-bit random nonce — unique per call
ciphertext = aesgcm.encrypt(nonce, plaintext.encode("utf-8"), None)
# Output stored as: base64(nonce[12] || ciphertext+tag)

2a.3 Digital Signatures — ECDSA P-256 Control Point J

Technical Mechanism. ECDSA (Elliptic Curve Digital Signature Algorithm) is an asymmetric signing algorithm standardised in FIPS 186-5 (NIST, 2023). The P-256 curve provides ~128 bits of security, equivalent to a 3072-bit RSA key (NIST, 2020). Signing computes a point multiplication on the elliptic curve using the private key and SHA-256 hash of the message; verification uses the corresponding public key.

Application. Every financial transaction is signed by security/tx_signing.py before database insertion. Deterministic JSON serialisation (sort_keys=True) ensures the same input always produces the same byte sequence: 

message   = json.dumps(tx_data, sort_keys=True).encode("utf-8")
signature = EC_PRIVATE_KEY.sign(message, ec.ECDSA(hashes.SHA256()))
# Returns base64-encoded DER signature — stored in transactions.signature

This provides non-repudiation: it is computationally infeasible to forge a signature without the private key, so each stored record constitutes cryptographic proof of server authorisation.

2a.4 Integrity Tagging — HMAC-SHA256 Control Point I

Technical Mechanism. HMAC applies a cryptographic hash function with a secret key to produce an integrity tag (Krawczyk et al., 1997): HMAC(K, m) = H((K⊕opad) || H((K⊕ipad) || m)). The result is a 256-bit tag that cannot be computed or forged without the secret key. Verification uses hmac.compare_digest() — a constant-time comparison that prevents timing side-channel attacks: 

def verify_hmac(tx_data: dict, tag_b64: str) -> bool:
    expected = base64.b64decode(compute_hmac(tx_data))
    provided = base64.b64decode(tag_b64)
    return hmac.compare_digest(expected, provided)  # constant-time — prevents timing attacks

ECDSA and HMAC are complementary: ECDSA provides public verifiability and non-repudiation; HMAC provides fast symmetric integrity checking for internal database consistency verification.

2b. Protocol-Level Security (30%)

Protocol-level security specifies how algorithms are combined, negotiated, and applied across communication channels between system components.

2b.1 Transport Security — HTTPS / TLS 1.3 Protocol Level

How the Protocol Works. TLS 1.3 (RFC 8446; Rescorla, 2018) performs a 1-RTT handshake using ECDHE key exchange, providing Perfect Forward Secrecy (PFS). All legacy cipher suites (RC4, 3DES, CBC-mode) are removed; only AEAD suites (AES-256-GCM, ChaCha20-Poly1305) are mandated. PFS ensures past sessions remain confidential even if the long-term private key is later compromised.

Implementation. Uvicorn is launched with an X.509 TLS certificate (keys/server.cert) and RSA-4096 key (keys/server.key). The minimum TLS version is explicitly enforced in main.py: 

ssl_context = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ssl_context.load_cert_chain(certfile="keys/server.cert", keyfile="keys/server.key")
ssl_context.minimum_version = ssl.TLSVersion.TLSv1_3   # Disables TLS 1.2 and below

All API traffic — passwords, JWT tokens, financial data, and MFA codes — is encrypted in transit, directly mitigating MitM and eavesdropping attacks. The cloud TiDB database also enforces TLS on port 4000.

2b.2 Authentication Protocol — RS256 JSON Web Tokens (JWT) Control Point E

How the Protocol Works. JSON Web Tokens (RFC 7519; Jones et al., 2015) consist of three Base64URL-encoded sections: header, payload (claims), and signature. RS256 (RSA+SHA-256) uses an asymmetric key pair: the private key signs at token issuance; the public key verifies on every request. This allows the public key to be distributed to any microservice without exposing the signing secret.

Implementation. The security/jwt_auth.py module issues 15-minute, role-encoded tokens: 

payload = {
    "sub": str(user_id),  # authenticated user ID
    "role": role,          # "customer" or "admin" — enforces RBAC at API gateway
    "iat": now,
    "exp": now + timedelta(minutes=15)   # short-lived — minimises theft window
}
return jwt.encode(payload, PRIVATE_KEY, algorithm="RS256")

2b.3 Multi-Factor Authentication — TOTP / RFC 6238 Control Point G

How the Protocol Works. TOTP (RFC 6238; M'Raihi et al., 2011) generates a 6-digit code: TOTP(K, T) = Truncate(HMAC-SHA1(K, T)), where T is the current UNIX time divided into 30-second windows. Both server and authenticator app independently compute this value — no network connection required during authentication. Codes are valid for 30 seconds with ±1 window tolerance for clock skew.

Implementation. SecureBank enforces TOTP as a mandatory second factor for both login and fund transfers. The login is explicitly two-step: /login returns a temporary user_id; the JWT is only issued upon successful TOTP verification at /mfa/verify. Transfers additionally re-verify TOTP at point-of-transaction, preventing session hijacking. The TOTP secret is stored AES-256-GCM encrypted (Section 2a.2) — creating defence-in-depth coupling.

2b.4 Secure Email — SMTPS / Implicit TLS (Port 465)

How the Protocol Works. SMTPS refers to SMTP over Implicit TLS on port 465, where TLS is established before any SMTP commands are exchanged. STARTTLS (port 587) begins with plaintext and upgrades — an active MitM attacker can strip the STARTTLS command, forcing the session unencrypted (a downgrade attack). Implicit TLS on port 465 is not susceptible to this class.

Implementation. The security/mail.py module uses smtplib.SMTP_SSL (Implicit TLS) to send transfer confirmation and security alert (new-IP login) emails, providing an out-of-band notification channel for anomaly detection.

2c. System-Level Security (30%)

System-level controls address threats that cryptography alone cannot prevent: brute-force attacks, privilege escalation, insider threats, and resource abuse.

2c.1 Intrusion Detection System — Software IDS Middleware

Role. An IDS is a detective control that monitors traffic for attack patterns. The prototype implements a software-equivalent via Starlette ASGI middleware (middleware/ids_monitor.py) that: (1) URL-decodes and inspects request paths against compiled regex signatures for SQLi (UNION SELECT, DROP TABLE), XSS (<script>, javascript:), and path traversal (../); (2) emits WARNING-level logs for matches identifying source IP; (3) logs all requests at INFO level with method, path, status code, and response duration. IDS is a detective control; rate limiting is the complementary preventative control.

2c.2 Rate Limiting and Account Lockout Control Point A

Two complementary controls resist brute-force and credential-stuffing attacks. IP-Level Rate Limiting via slowapi limits /login to 100 req/15 min, /mfa/verify to 10/min, and /mfa/confirm to 5/min (HTTP 429 on breach). Account Lockout locks the account database-side for 15 minutes after 5 consecutive failed password attempts — independent of IP rotation. A Fraud Rules Engine additionally flags transfers exceeding LKR 5,000 for administrator review, simulating AML threshold monitoring (FATF, 2012).

2c.3 Role-Based Access Control (RBAC) and Least Privilege Control Points H & E

Application-Level RBAC. The JWT role claim ("customer" / "admin") is verified server-side on every request via require_admin dependency. Administrators cannot initiate transfers; customers cannot access audit logs or fraud queues. Database Least Privilege: schema.sql creates two restricted DB users — account_service (SELECT/UPDATE on accounts, SELECT on ledger) and transaction_service (SELECT/INSERT/UPDATE on transactions & ledger). Neither holds DELETE, DROP, or DDL privileges, limiting blast radius of a compromise (NIST, 2018).

2c.4 Comprehensive Audit Logging

Every security-relevant event invokes the _audit() helper, inserting an audit_log record with event_type, user_id, descriptive detail, ip_address, and DB-generated created_at timestamp. 16 distinct event types are logged (REGISTER, LOGIN_FAIL, ACCOUNT_LOCKED, TRANSFER, FRAUD_FLAG, etc.). The audit endpoint is admin-only, supporting forensic investigation and compliance with PCI DSS requirements (PCI SSC, 2022).

2c.5 Account Freeze (User-Initiated Kill Switch)

Users can self-service freeze their account via the dashboard, setting users.is_frozen = TRUE instantly. This blocks all further logins, MFA operations, and fund transfers until an administrator explicitly unfreezes the account — analogous to a bank card block, providing rapid incident response without requiring customer support intervention.

5. Critical Evaluation

5.1 Strengths of the Implementation

The SecureBank prototype demonstrates a coherent, layered security architecture that addresses the principal attack surfaces of an internet-facing financial application. The selection of Argon2id over bcrypt or SHA-256 reflects current best practice from OWASP and NIST, with memory-hardness parameters (19 MB, time_cost=2) correctly calibrated to resist GPU-accelerated offline cracking. The use of AES-256-GCM for field-level encryption is particularly noteworthy: GCM's integrated authentication tag means any database-level tampering with ciphertext is detected at decryption time — a form of cryptographic data integrity absent from simpler "encrypt at rest" implementations.

The choice of RS256 (asymmetric) over HS256 (symmetric) for JWT signing is architecturally sound: in a microservices context, the public key can be distributed to downstream services without exposing the signing secret. The 15-minute token expiry is appropriately short for a financial application. Critically, mandatory TOTP re-verification at the point of transaction (not merely at login) constitutes defence-in-depth: even if an attacker obtains a valid JWT from an open session, they cannot move funds without concurrent physical access to the victim's TOTP device.

The use of Implicit TLS (port 465) for SMTP rather than STARTTLS (port 587) demonstrates protocol-level awareness that distinguishes the implementation from a naive "just use TLS" approach, specifically preventing STARTTLS downgrade attacks.

5.2 Limitations and Areas for Improvement

Key Management. The most significant limitation is that the AES-256-GCM encryption key and HMAC key are stored as environment variables in a plaintext .env file. In production, these must reside in a Hardware Security Module (HSM) or cloud KMS (AWS KMS, HashiCorp Vault). A full server compromise including the .env file would allow all encrypted fields to be decrypted — the encryption provides database-layer protection only.

Self-Signed Certificate. The TLS certificate is self-signed (OpenSSL), providing encryption in transit but no third-party identity verification. Browsers display security warnings, and the certificate cannot be revoked via CRL or OCSP. Production deployment requires a CA-issued certificate (e.g., Let's Encrypt).

IDS Capability. The IDS middleware inspects only the request URL, not the request body. An attacker submitting SQLi payloads in a JSON body field would not be detected (though parameterised queries prevent execution). A production WAF would perform deep body inspection, and the current IDS is detective-only — integration with a firewall API would enable automated IP blocklisting as a preventative control.

JWT Revocation. Stateless JWTs cannot be invalidated before 15-minute expiry without a server-side token blacklist (e.g., Redis-backed) or refresh-token rotation. The account freeze control partially mitigates this — frozen accounts reject API requests at database level regardless of JWT validity.

Audit Log Hash Chaining. The architecture documentation describes a SHA-256 hash chaining mechanism for tamper-evident audit logs. However, the current _audit() helper function does not implement the hash chain computation, representing a gap between design intent and implementation that reduces non-repudiation strength.

No Network-Level Firewall. The prototype operates without a hardware or OS-level firewall. A production cloud deployment would require AWS Security Groups or UFW rules restricting ingress to ports 443/8443 only.

6. Conclusion

SecureBank demonstrates a functionally complete and technically substantive implementation of multi-layer security for a prototype banking application. At the algorithm level, the system correctly applies Argon2id for password hashing, AES-256-GCM for authenticated field-level encryption, ECDSA P-256 for transaction non-repudiation, and HMAC-SHA256 for symmetric integrity tagging. At the protocol level, TLS 1.3 secures all transport channels, RS256 JWT provides stateless authenticated authorisation, TOTP per RFC 6238 enforces two-factor authentication for both login and transactions, and SMTPS provides a secure out-of-band notification channel. At the system level, an IDS middleware provides real-time threat detection, rate limiting and account lockout resist brute-force attacks, RBAC with JWT role claims enforces privilege separation, and least-privilege database user provisioning minimises insider threat and injection impact.

Each control maps directly to a vulnerability point identified in the CW1 system design, demonstrating continuity between design and implementation phases. The critical evaluation in Section 5 identifies areas requiring further investment — particularly key management, certificate infrastructure, IDS body inspection, and JWT revocation — characteristic of a prototype built within time and resource constraints. Collectively, the implementation illustrates that security must be addressed as a layered, integrated concern: the strength of the SecureBank security posture arises from the interlocking nature of its controls, where each layer compensates for the limitations of the others.
